Это уже не официальный Boston Dynamics API, а предлагаемый вами внутренний контракт.

```python
class ETDRuntime:
    def load_package(self, manifest_path: str) -> SkillHandle: ...
    def validate_package(self, skill: SkillHandle) -> ValidationReport: ...
    def activate_skill(self, skill_id: str, job_context: dict) -> ActivationResult: ...
    def execute_skill(self, skill_id: str, state: RobotState) -> SkillCommand: ...
    def abort_skill(self, skill_id: str, reason: str) -> None: ...
    def get_metrics(self, skill_id: str) -> dict: ...
```

`SkillCommand` должен быть высокоуровневым, например:

```json
{
  "body_mode": "stable_reach",
  "arm_mode": "guarded_arc",
  "wrist_mode": "soft_contact",
  "target_pose": [0.62, -0.14, 1.08],
  "speed_profile": "industrial_safe",
  "force_profile": "fragile",
  "timeout_sec": 12
}
```

То есть ETD-пакет не говорит мотору “подай 18 Н·м”, а говорит core system:  
“выполни guarded arc к target pose с таким профилем контакта”.

## 10. Ограничения безопасности

Правило должно быть жёстким:

**ETD package cannot override robot safety kernel.**

То есть пакет может:
- просить режим;
- задавать желаемый профиль;
- предлагать primitive;
- оценивать task-fit;
- вызывать fallback.

Но пакет не может:
- отключать collision avoidance;
- снимать torque limits;
- менять certified stopping behavior;
- самовольно игнорировать human-presence logic;
- переписывать low-level locomotion controller.

Это особенно важно для гуманоидов на заводе и рядом с человеком.

## 2. Как это должно быть устроено в ETD-модели

Для ETD я бы не делал один вариант “или всё open-source, или всё коммерческое”. Правильная модель — **гибридная**:

| Тип пакета | Код | Цена | Для чего |

## 3. Как защищать платные skill-пакеты

Если skill продаётся, его нельзя защищать только “закрытием кода”. Для роботов нужна защита в несколько слоёв:

1. **Package signing** — пакет подписан издателем, runtime проверяет подпись.
2. **Hash manifest** — фиксируются контрольные суммы файлов.
3. **License entitlement** — право установки привязано к организации, роботу, флоту или станции.
4. **Robot serial binding** — пакет работает только на разрешённых роботах.
5. **Station binding** — пакет работает только на утверждённых workcell/station profiles.
6. **Encrypted payload** — закрытые модели, веса, политики и рецепты могут быть зашифрованы.
7. **Readable safety metadata** — safety/capability/manifest должны оставаться читаемыми для проверки.
8. **Revocation list** — магазин может отозвать пакет.
9. **Audit log** — фиксируется кто, где, на каком роботе запускал навык.
10. **Sandbox/capability firewall** — пакет не может получить доступ к servo torque, emergency stop override, collision disable, balance core override.

Это особенно важно из-за физического риска. 3DNews ранее писал о найденной уязвимости UniPwn в роботах Unitree, затрагивавшей Go2, B2, G1 и H1, что показывает: магазин навыков для роботов должен иметь более строгую security/governance-модель, чем обычный магазин приложений. ([3DNews - Daily Digital Digest](https://3dnews.ru/1129873/issledovateli-obnarugili-chervya-prevrashchayushchego-robotov-unitree-v-armiyu-zombi?utm_source=chatgpt.com))

Главное правило: **коммерческий пакет может скрывать свою интеллектуальную собственность, но не может скрывать safety-декларации**. Runtime обязан видеть, какие capabilities запрашивает пакет, какие ограничения есть, какие fallback-сценарии предусмотрены и где пакет разрешён к запуску.
